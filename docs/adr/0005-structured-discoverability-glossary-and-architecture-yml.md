# 0005. Structured discoverability layer: GLOSSARY.md + architecture.yml

**Date:** 2026-05-26
**Status:** accepted
**Deciders:** Filip Podstavec

## Context

`AGENTS.md` (canonical, prose) + AIDEV anchors (in-code, grep-able) cover
two of the three things a next agent needs to safely modify an unfamiliar
repo:

1. **Why** the architecture looks the way it does — `docs/adr/`
2. **How** to operate the repo (conventions, commands, gotchas) — `AGENTS.md`

The third thing — **what domain terms mean in *this* repo and how the
top-level modules relate to each other in machine-readable form** — was
gappy. The failure modes we observed:

- **Domain-term hallucination.** Agents confidently invent meaning for
  "tenant" / "invoice" / "session" / "lead" based on prior priors instead
  of this repo's actual semantics. AGENTS.md prose tells the agent *to
  look at the code* but doesn't give a one-line anchor per term. Reading
  source to recover meaning every time is O(N) per term per session.
- **Module-role ambiguity.** AGENTS.md says "repo layout" in 10 lines of
  prose. That's fine for orientation, but agents proposing refactors
  often need structured answers like "is `scripts/hooks/` stable or
  experimental?" / "what's the public surface I shouldn't rename?" /
  "what module does `agents/` pair with for Codex parity?". Re-deriving
  those answers from prose + tree walks is wasted tokens every session.

Industry signal (mid-2026): AGENTS.md per folder is the convergent
standard (OpenAI ships 88 files in its main repo; 60K+ public repos use
AGENTS.md across Codex/Cursor/Copilot). Pure-YAML-per-folder
(`module-meta.yml` in every dir) is not widely adopted — Cursor's
`.cursor/rules/*.mdc` uses YAML *frontmatter on top of* prose, not as
replacement. Human-curated AGENTS.md beats LLM-generated by ~4pp on task
success (Augment Code 2026 study).

We need to close the two gaps **without** breaking the AGENTS.md
convention, and without adding maintenance that bit-rots on every
commit.

## Decision

We add two complementary artifacts to the discoverability layer:

1. **`GLOSSARY.md` at repo root** — domain terms specific to *this* repo,
   one entry per term: 1–2 sentence definition, optional aliases,
   optional code-path pointers. Human-curated; the `/glossary-init`
   skill surfaces candidates by frequency analysis of identifiers but
   never invents definitions.
2. **`architecture.yml` at repo root** — machine-readable structured
   metadata about top-level modules: `path` + `role` + `stability` +
   optional `public_surface` / `depends_on` / `paired_with` / `owners`.
   Versioned schema (`v1`). The `/arch-map` skill bootstraps a draft
   from directory walk + AGENTS.md hints; the user fills `role` per
   module.

Both files live at repo root, parallel with `AGENTS.md` (not under
`docs/`). Agents read root first; these files are referenced often
enough that the extra path component is friction.

Neither file is auto-generated, auto-fired by a hook, or
auto-refreshed on commit. Both follow ADR 0004's user/agent-invoked
philosophy: the agent recognizes the moment and runs the skill.

## Consequences

### Positive

- **One-shot domain disambiguation.** First grep of `GLOSSARY.md`
  removes a class of hallucination ("what does Lead mean here?") that
  re-reading code in every session would not.
- **Structured module queries.** Agents can answer "which modules are
  `stable`?" / "what's `agents/`'s public surface?" with one YAML load,
  not a tree walk + AGENTS.md parse per query.
- **Cross-tool by construction.** Both files are plain text at repo
  root; both Claude Code (via `@AGENTS.md` mention or direct Read) and
  Codex (via native AGENTS.md merge or direct Read) see them.
- **No new failure modes from staleness.** Domain terms change slowly
  (the few that matter are load-bearing for years); module roles change
  during refactors that humans already drive. Neither artifact tries to
  track granular code changes.
- **Honest scope.** Neither replaces AGENTS.md, per-folder AGENTS.md, or
  ADRs. They sit alongside as the *structured-metadata* layer the
  prose-and-anchors layer didn't cover.

### Negative

- **Two more files for users to maintain.** Mitigated by: both are
  user-invoked (no nudge spam), both have idempotent skills for adding
  entries, both have minimal required fields (`path` + `role` +
  `stability` for arch-map; `term` + 1 sentence for glossary).
- **Risk of bit-rot if the user adopts but never updates.** Mitigated by
  scoping: glossary tracks ~10–30 load-bearing domain terms, not every
  identifier; arch-map tracks top-level modules, not every file.
  Future `/stack-check` extension can validate schema + flag entries
  that reference paths no longer in the repo.
- **YAML for architecture.yml introduces parsing surface.** We use a
  flat schema (no anchors, no merge keys, no multi-line scalars
  required) so a stdlib-only parser is enough. The skill validates
  the file before writing.

## Alternatives considered

- **YAML metadata per folder (`<dir>/module.yml` in every subdir)** —
  rejected. Not the 2026 convergent standard; AGENTS.md per folder is.
  Cursor's `.cursor/rules/*.mdc` *combines* YAML frontmatter with prose,
  but treats prose as primary. Forcing structured metadata into every
  subfolder creates maintenance debt out of proportion to the
  discoverability win.
- **Embed glossary + arch-map inside AGENTS.md** — rejected.
  AGENTS.md is prose and runs against Codex's 32 KiB cap. Adding
  structured terms + module metadata inline would push large repos over
  the cap; separating keeps each file's scope clean.
- **Auto-generate both from code** (frequency-only glossary, import-graph
  arch-map) — rejected. Auto-generated AGENTS-style files lose 0.5–2pp
  on task success vs. human-curated (per Augment Code 2026 study).
  Skill *surfaces candidates*; user *picks and defines*.
- **Put both under `docs/`** — rejected. Agents check root first, root
  second, deep dirs third. Glossary and arch-map are referenced often
  enough to warrant root residence — same logic that put AGENTS.md at
  root, not under `docs/conventions/`.
- **Sidecar JSON instead of YAML** — rejected for architecture.yml.
  Humans hand-edit this file; YAML is more comfortable to read and
  diff. We retain JSON for fully-machine files (`plugin.json`,
  `marketplace.json`).
